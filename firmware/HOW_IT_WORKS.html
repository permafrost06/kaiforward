Nokia 8110 4G / GerdaOS / KaiForward

Native firmware and IP call relay

The installed implementation: native framebuffer UI, durable SMS forwarding over Wi-Fi, and browser call control with duplex cellular audio.

Implementation snapshot · 13 October 2026 · Nokia TA-1059 · Kernel 3.10.49-kaiforward+
Code excerpts omit surrounding validation/error handling. Source links are relative to this file in firmware/.

01 · Architecture

Gecko/B2G no longer owns the phone UI or the radio client. Native C programs run under Android init. Gerda's Android services, Qualcomm RIL libraries, audio HAL, and the original modem firmware remain underneath them. The PC runs Python services and browser interfaces.

BoundaryImplementationResponsibility
Phone / UIkaiforward-native --uiFramebuffer, keypad, status, settings.
Phone / radiokaiforward-nativeOwn both RIL sockets; receive SMS; maintain SIM/call state; execute call operations.
Phone / uploadkaiforward-native --uploadUpload pending SQLite records independently of radio handling.
Phone / Wi-Fiwifi.sh, supplicant, DHCPAssociation, IP address, routes, DNS, reconnect.
Phone / callskaiforward-relayTLS session, local call controller, AudioPolicy, PCM capture/playback.
PC / SMSreceiver.py, viewer.pyAuthenticated archive writes and browser archive access.
PC / callscall_relay.py, browser AudioWorkletCall commands, state, microphone and speaker streaming.

SMS and calls have separate network sessions. SMS is store-and-forward HTTPS; calls use live PCM and command frames over one TLS/TCP connection. The browser uses a local WebSocket. There is no SIP server, RTP stream, WebRTC peer connection, or KaiOS app in this path. USB/ADB is used for maintenance, not runtime audio transport.

02 · Boot and native UI

The bootloader loads the kernel and ramdisk; init imports the native service declarations. The image disables B2G, rilproxy and the API daemon. The native service processes start in class main; keeping UI, radio, upload and relay separate prevents network or rendering work from blocking SMS reception.

service kaiforward-sms /system/bin/kaiforward-native
    class main
    user root
    group root radio log

service kf-relay /system/bin/kaiforward-relay
    class main
    user root
    group root audio inet

ui.c reads framebuffer geometry, maps display memory, draws text in C, and consumes Linux key events. It reads battery information from sysfs and service status from local files.

int fb = open("/dev/graphics/fb0", O_RDWR);
/* Geometry ioctls occur before the mapping. */
unsigned char *mem = mmap(NULL, fix.smem_len,
    PROT_READ | PROT_WRITE, MAP_SHARED, fb, 0);

Incoming calls and new SMS wake the screen; inactivity blanks it after 30 seconds. Blanking is not full system suspend. The native keypad interface implements status/settings; the tested call controls are in the PC browser.

03 · Wi-Fi and configuration

The UI saves this key/value configuration atomically to /data/kaiforward/config. The directory is root-private. Password and token characters remain visible while editing, as requested.

# Shape of the configuration; credentials below are placeholders.
ssid=YOUR_WIFI_SSID
password=YOUR_WIFI_PASSWORD
url=https://192.168.0.122:8767/v1/messages
token=YOUR_ACCESS_TOKEN
device_id=nokia-8110
  1. wifi.sh loads the matching Wi-Fi module, configures wlan0, writes the private supplicant configuration and launches wpa_supplicant.
  2. wifi.c scans and reads network results through the supplicant control interface.
  3. BusyBox udhcpc obtains a lease. Its udhcpc.sh hook applies the address/subnet and configures Android netd routes, default network and DNS.
  4. The Wi-Fi supervisor reconnects after process failure or configuration changes. The phone initiates both PC connections.

The call helper derives its default host from the SMS URL and uses port 8769; its CLI also accepts endpoint overrides. The settings screen does not expose a separate call endpoint. Changing the PC address also requires the receiver bind address and certificate to match; the phone validates the hostname/IP against /data/kaiforward/ca.pem.

Source: wifi.sh · wifi.c · udhcpc.sh · common.c · relay.c

04 · Modem and RIL

The modem firmware was retained. Cellular signaling still runs in the modem; Gerda's Qualcomm vendor libraries and rild expose Android Radio Interface Layer parcels through /dev/socket/rild and rild2, one per SIM slot.

The native radio process owns both connections. It requests SIM/app and registration state, parses unsolicited SMS/call/network events, and requests the current call list after call-state changes. SIM status is based on modem responses, rather than a hardcoded “registered” label.

The relay does not become another RIL client. It asks the existing radio process through the private controller socket, so adding calls does not displace the SMS connection.

05 · SMS reception and durability

  1. A RIL SMS event supplies an encoded PDU and SIM slot.
  2. sms.c decodes sender, timestamp and GSM/UCS-2 text. store.c retains raw PDUs, deduplicates records and assembles multipart messages.
  3. The SQLite transaction commits to /data/kaiforward/native.sqlite3.
  4. Only then does the radio process positively acknowledge reception to the modem.
/* radio.c: reception branch */
int rc = store_pdu(db, r->slot, pdu);
ack(r, rc == 0);
PRAGMA journal_mode=WAL;
PRAGMA synchronous=FULL;

The local archive keeps raw, multipart and completed-message records. Unsupported PDUs remain retained; incomplete multipart messages wait for the remaining parts. Received counts completed messages; Queued counts pending uploads. Marking a message uploaded does not delete its local record.

Source: radio.c · sms.c · store.c

06 · HTTPS upload and PC archive

The independent uploader reads pending records, builds JSON and invokes native curl with private configuration. HTTPS verifies the PC certificate; a bearer token authenticates the device. The installed receiver URL is https://192.168.0.122:8767/v1/messages.

receiver.py validates identity, token and payload, writes to data/sms.sqlite3, commits, then returns accepted message keys. The unique (device_id, message_key) key makes retries idempotent; conflicting payloads under an existing key are rejected. Native IDs use an offset of 1,000,000,000 to coexist with the earlier KaiOS archive.

/* upload.c: response validation before marking the local row uploaded */
if (extra != EOF || bad || memchr(reply, 0, size) || !ack_valid(reply, key))
    return -1;
return store_ack(db, id) ? -1 : 1;

Failed delivery leaves the local row pending. Retry backoff grows from 20 to 300 seconds; Sync requests an immediate attempt. These are two distinct acknowledgements: modem ACK = committed on phone; upload ACK = committed on PC.

The archive is available at http://127.0.0.1:8766. viewer.py reads the database; the React interface in viewer-ui/src/App.tsx displays it.

Source: upload.c · store.c · receiver.py · viewer.py · App.tsx

07 · Call transport protocol

The phone opens TLS/TCP to the PC on 8769 using Mbed TLS. Certificate-chain and hostname verification precede the protocol HELLO, which supplies protocol version 1, device ID and token. The PC checks the private identity/token using hmac.compare_digest; the browser never receives those credentials.

mbedtls_ssl_conf_authmode(&options, MBEDTLS_SSL_VERIFY_REQUIRED);
mbedtls_ssl_conf_ca_chain(&options, &certificates, NULL);
/* ssl_set_hostname(), connect(), handshake(), verify_result() follow. */

Every frame is uint32_be length | uint8 type | payload. Length includes the type byte and must be between 1 and 8192. Commands/results begin with a big-endian 32-bit operation ID. Framing handles TCP fragmentation/coalescing; it does not assume one read equals one packet.

def encode_frame(kind, payload=b''):
    if not 1 <= kind <= 9 or len(payload) + 1 > MAX_FRAME:
        raise ValueError('Invalid phone frame')
    return struct.pack('>I', len(payload) + 1) + bytes([kind]) + payload
TypeDirectionPayload
1 HELLOBothJSON credentials; then {"ok":true}.
2 STATEPhone → PCJSON: two slots, call state/count/index, registration, media state/error.
3 DOWNLINKPhone → PC320 bytes of caller PCM.
4 COMMANDPC → phoneOperation ID + ASCII, e.g. 2 answer.
5 RESULTPhone → PCOperation ID + JSON result.
6 STARTPC → phoneOne byte: selected slot, 1 or 2.
7 STOPPC → phoneEmpty; releases relay audio.
8 UPLINKPC → phone320 bytes of microphone PCM.
9 PINGPC → phoneEmpty acknowledgement/heartbeat.

Phone state is sent approximately once per second. The PC acknowledges it and broadcasts public state over the browser WebSocket at /call. Only one browser owns audio at a time.

08 · Answer, dial and hangup

  1. An incoming-call event causes the radio owner to query RIL_REQUEST_GET_CURRENT_CALLS (9). Its report updates the browser.
  2. Answer first obtains browser microphone permission and attaches audio. JavaScript submits the call command over the local WebSocket.
  3. The PC validates the operation, allocates an operation ID, and sends a TLS COMMAND frame.
  4. The phone relay submits the ASCII command to /data/kaiforward/call.sock, a SOCK_SEQPACKET socket with mode 0600 and peer-credential checks.
  5. The radio owner validates current call state and sends the appropriate RIL request. The result returns under the same operation ID.
if (action == 1 && r->calls == 1 && r->call_state == 4)
    code = 40; /* RIL_REQUEST_ANSWER */
else if (action == 2 && r->calls == 1 && r->call_index > 0) {
    code = 12; /* RIL_REQUEST_HANGUP: an explicit call index */
    put(args, 1);
    put(args + 4, r->call_index);
    size = 8;
}

Dial uses RIL request 10 and requires an idle registered slot. Answer/hangup reject ambiguous multiple-call state. The PC serializes operations and waits up to nine seconds for a result. Disconnect/timeouts report an unknown outcome; dial/answer/hangup are never automatically replayed.

Attaching browser audio does not immediately open PCM. The PC sends START only after the selected slot reports one active call and media is idle.

Source: app.js · call_relay.py · call.c · radio.c

09 · Audio policy and Binder dependencies

The relay calls Android's existing media.audio_policy Binder service to enter MODE_IN_CALL (2), then returns to MODE_NORMAL (0). The vendor audio HAL establishes the cellular voice path.

utility("/system/bin/service", "call", "media.audio_policy", "3", "i32",
        in_call ? "2" : "0", output, sizeof(output));
/* Transaction 3 is SET_PHONE_STATE on this Android audio-policy ABI. */

Removing Gecko exposed two dependencies: mediaserver camera initialization waited for SurfaceFlinger; audio permission checks waited for a Binder permission controller. Those waits blocked audio setup and then QCRIL's audio-related work, which also delayed SMS and hangup events.

kf-display runs Gerda's SurfaceFlinger to satisfy the display-service dependency. The native framebuffer process still draws the phone UI. kf-permission supplies the narrow permission controller:

if (requester != 0 && requester != 1000 && requester != 1013) return 0;
if (uid != 0 && uid != 1000 && uid != 1001 && uid != 1013) return 0;
return !strcmp(name, "android.permission.MODIFY_AUDIO_SETTINGS");

The relevant UIDs are root (0), system (1000), radio (1001), media (1013). This restores the required audio permission for the trusted stack rather than granting arbitrary permissions.

10 · Kernel voice-session correction

The original Gerda voc_start_playback selection handled legacy Voice/Voice2/VoLTE but omitted VoiceMMode1/2. On this phone a SIM 2 call used VoiceMMode1, so playback could report success without selecting the active call's CVS session.

if (port_id == VOICE_PLAYBACK_TX)
    return session_id == VOICE_SESSION_VSID ||
           session_id == VOLTE_SESSION_VSID ||
           session_id == VOWLAN_SESSION_VSID ||
           session_id == VOICEMMODE1_VSID;
if (port_id == VOICE2_PLAYBACK_TX)
    return session_id == VOICE2_SESSION_VSID ||
           session_id == VOICEMMODE2_VSID;

The patch adds the missing session families, preserves locking/reference-count and handover bookkeeping, and returns errors when playback has no usable active session. The relay selects the injection route from the running voice PCM: VoiceMMode1 is device 27; VoiceMMode2 is device 28. Legacy session devices are also considered.

Voice session number ≠ physical SIM slot. SIM 2 used VoiceMMode1 in the successful test. Route selection follows the active voice session, not a slot-number assumption.

The installed kernel is 3.10.49-kaiforward+. It retains Gerda's appended device trees and uses matching rebuilt modules. The modem firmware and calibration partitions were not replaced.

Source: kaiforward_incall_playback.h · apply_kernel_patch.py · prepare_call_kernel.py · pcm.c

11 · Duplex PCM audio

Transport audio is mono signed 16-bit little-endian PCM at 8 kHz. Each 20 ms frame contains 160 samples × 2 bytes = 320 bytes; raw payload bandwidth is 128 kbit/s per direction. There is no audio compression or recording archive.

StageInterface / format
Cellular downlink captureMultiMedia1 Mixer VOC_REC_DL → /dev/snd/pcmC0D0c; 8 kHz S16_LE mono.
Phone ↔ PC ↔ browser320-byte PCM frames; TLS/TCP on the LAN; WebSocket on PC loopback.
Browser speakerAudioWorklet jitter buffer and linear resampling to the AudioContext output rate.
Browser microphonegetUserMedia → AudioWorklet → 8 kHz S16 frames.
Cellular uplink injection/dev/snd/pcmC0D1p; 48 kHz S16_LE mono → selected In-call Music mixer → active modem voice session.

Caller → PC

The relay checks for exactly one active voice-session family, closed multimedia PCMs and unused routes, then enables capture and injection. A capture child reads ALSA through direct ioctls; the parent sends DOWNLINK frames. The PC forwards them to the audio-owner browser.

The AudioWorklet starts playback with approximately 60 ms buffered, resamples to the browser's actual output rate, and discards old buffered audio when delay exceeds roughly 160 ms. It emits silence during underrun.

PC → caller

The browser requests a mono microphone with echo cancellation, noise suppression and automatic gain. The AudioWorklet averages input samples into the 8 kHz stream, quantizes to signed 16-bit, and transfers each completed frame to the page:

if (this.used === 160) {
    const buffer = this.packet.buffer;
    this.port.postMessage(buffer, [buffer]);
    this.packet = new Int16Array(160);
    this.used = 0;
}

The PC sends these as UPLINK. The phone playback child linearly interpolates 160 samples into 960 samples for the 48 kHz injection PCM:

for (int i = 0; i < 160; i++) {
    for (int j = 0; j < 6; j++)
        output[i * 6 + j] = last + (input[i] - last) * (j + 1) / 6;
    last = input[i];
}

The 48 kHz conversion satisfies the device interface; it does not restore bandwidth beyond the 8 kHz transport. The kernel correction connects the In-call Music playback stream to the active cellular uplink.

Concurrency and latency

Capture and playback run in separate forked children, with nonblocking bounded pipes to the TLS parent. Blocking ALSA I/O cannot stall network parsing. Phone capture drains accumulated frames and sends the newest; uplink queues and browser/server send buffers drop delayed audio rather than grow latency.

12 · Cleanup and failure behavior

EventBehavior
Browser Hang upStop relay PCM, send RIL hangup for the explicit call index, refresh call state.
Caller hangs upRIL event updates the call list; relay detects no active call and tears down PCM/routes.
Disable audio / close browserStop microphone tracks and relay PCM. This releases audio; it does not issue a cellular hangup.
Wi-Fi / PC session lossNo received relay traffic for eight seconds triggers session cleanup and reconnection. Cellular call control is not replayed.
PCM child failureStop both children, release routes and report media error.
SMS receiver offlineKeep pending rows on disk and retry; SMS reception continues independently.
 
void audio_stop(CallAudio *a) {
    reap(&a->capture_pid);
    reap(&a->playback_pid);
    if (a->capture >= 0) close(a->capture);
    if (a->playback >= 0) close(a->playback);
    if (a->routes) {
        mixer(injection(a->session), 0);
        mixer("MultiMedia1 Mixer VOC_REC_DL", 0);
    }
    memset(a, 0, sizeof(*a));
    a->capture = a->playback = -1;
}

AudioPolicy returns to normal when calls end; relay-session cleanup also restores it if the helper had entered call mode. PCM cleanup closes streams and switches mixer routes off. No captured call audio is persisted.

13 · Build and recovery

  1. build_native.py cross-compiles the C core with SQLite for ARM Cortex-A7 using the musl toolchain.
  2. build_call_relay.py builds the static relay with Mbed TLS 3.6.7 from a checksum-verified source archive.
  3. The kernel scripts apply the voice playback correction and build the kernel/modules. prepare_call_kernel.py retains the working native ramdisk and Gerda's original 46 appended device trees; module release/symbol CRC checks protect compatibility.
  4. build_native_image.py assembles boot/system images, disables Gecko startup, installs native programs and validates startup entries, hashes, executable permissions and filesystem consistency.
  5. package_recovery.py signs the recovery installer. Installation updates boot/system while retaining settings/SMS under /data.

The initial recovery loop was caused by host staging permissions: ramdisk root/mount directories became 0700, preventing non-root critical services from traversing them. Their correct mode is 0755. That was independent of the modem firmware.

SD-card packagePurpose

The running phone was updated and readback-checked in stages. The assembled complete boot/system package has been validated, but its full system image has not itself been flashed. Modem, calibration, recovery and bootloader partitions were preserved.

The owner confirmed two-way audio and browser hangup on SIM 2. Caller hangup cleared and SMS reception advanced correctly. After the call, both PCM streams were closed, capture/injection mixers were off and AudioPolicy was normal. Automatic relay startup and Wi-Fi/TLS reconnection after reboot were verified. The last archive check showed four native messages uploaded with queue zero.

Outgoing dialing is implemented but not carrier-tested. SIM 1 calls, multiple-call/call-waiting handling, handovers and long unattended operation remain unverified. Call controls deliberately reject ambiguous multiple-call state. Caller-number presentation and a complete native phone dialer/ringtone workflow are not implemented.
